Tablas de páginas y RAM

Qué se ejecuta

    Enlazado estático

    ld *.o -lc -lm

    El enlazador busca las externas indefinidas (por ejemplo printf, que a su vez necesita write) en libc.a y copia esas funciones dentro del ejecutable.

    prog1: código + copia de libgráf
    prog2: código + copia de libgráf
    prog3: código + copia de libgráf
    • + Al cargarlo, todo lo que necesita ya está ahí.
    • + Solo incluye las funciones que se llaman.
    • − Con 20–50 MB de bibliotecas gráficas en cientos de programas, se desperdicia muchísimo disco y también RAM (el SO no sabe que puede compartirlas).
    • − Para corregir un error de la biblioteca hay que volver a enlazar cada programa.

    Biblioteca compartida (DLL)

    El enlazador pone una pequeña rutina auxiliar que se vincula con la función en tiempo de ejecución. La biblioteca se carga al arrancar el programa o en la primera llamada, y si otro programa ya la cargó, se reutiliza.

    prog1: código + rutina auxiliar →
    prog2: código + rutina auxiliar →
    libgráf: UNA sola copia en RAM, paginada bajo demanda
    • + Ejecutables más chicos y una sola copia en memoria.
    • + No se carga entera: se pagina una página a la vez, y las funciones que no se llaman no entran a la RAM.
    • + Si se corrige la DLL (por ejemplo, con Windows Update), todos los programas usan la versión nueva la próxima vez que arrancan, sin recompilar.
    • − El «pequeño problema»: la biblioteca queda en una dirección virtual distinta en cada proceso (abajo).

    Código independiente de la posición

    Se compila la biblioteca con una bandera especial: sin direcciones absolutas, solo saltos relativos («saltar n bytes hacia adelante o hacia atrás»).

    absoluto: JMP 36K+16 ← sirve solo para el proceso 1
    relativo: JMP +16 desde el inicio ← sirve en cualquier lado
    • + Funciona en cualquier dirección virtual: la biblioteca se comparte de verdad.
    • − Otra salida sería copia en escritura y reubicar cada copia, pero eso arruina el propósito de compartir.

    Ideas clave para el examen

    • Solo se comparten de entrada las páginas de solo lectura, como el texto del programa. Con espacios I y D separados es fácil: los procesos usan la misma tabla del espacio I y una tabla propia para el espacio D (fig. 3-26). ⚠️ Si el SO desaloja todas las páginas de A, el otro proceso que las compartía empieza a dar fallos. Al terminar A, hay que saber que las páginas siguen en uso para no liberarlas.
    • Copia en escritura: después de un fork no se copia nada. Padre e hijo apuntan a los mismos marcos, todos en SOLO LECTURA. La primera escritura produce un trap por violación de protección; el SO copia solo esa página y deja las dos copias en LECTURA-ESCRITURA. Las páginas que nunca se escriben (todo el código) no se copian nunca.
    • 🧠 Conexión con la U2: con fork + execve el hijo descarta enseguida todo su espacio. Sin copia en escritura, el fork habría copiado todo para nada.
    • Bibliotecas compartidas (DLL): una sola copia en RAM, paginada bajo demanda, y se actualizan sin recompilar. ⚠️ El «pequeño problema»: cada proceso la ve en otra dirección virtual. La solución es el código independiente de la posición (solo saltos relativos). La dirección física no importa: la resuelve la MMU.
